What this is

A prompt market plus a constrained implementation sandbox

Participants submit prompt candidates as GitHub Issues. Votes rank those prompts. If a real prompt beats the weekly no-change baseline, the selected prompt is given to the implementation agent, which may edit only lab/index.html, lab/style.css, and lab/app.js.

The landing page explains the experiment. The lab is the changing implementation target. That separation keeps the public explanation stable while still allowing visible weekly changes.

This is not a feature-request queue, a paid merge system, or a general-purpose web app builder. The AI agent can propose changes, but final adoption stays manual.

Design choice

The experiment is deliberately narrow

Less surface area makes the run easier to inspect. The whole point is stable comparison: same scope, same safety boundary, visible PRs, and recorded outcomes.

Loop

How the experiment runs

Propose

Create a GitHub Issue with the exact prompt and expected visible result.

Vote

Use GitHub reactions. A real prompt must beat the 20-vote baseline.

Run

The selected prompt is given to the fixed implementation agent.

Check

Safety and static-site checks run before the implementation PR is proposed.

Review

The maintainer reviews the PR and decides merge, reject, unsafe, failed, or no-change.

Record

The result and expectation gap are logged for later comparison.

Safety boundary

The AI is not given a blank check

The point is not to let an agent do anything. The point is to test whether useful changes emerge under stable, reviewable constraints.

Allowed local behavior

Static HTML, CSS, vanilla JavaScript, helper functions, local state, and JSON export/import inside the lab.

Blocked runtime behavior

No external scripts, CDNs, network fetches, WebSockets, cookies, iframes, eval, new Function(...), or hidden trackers.

Manual adoption

The AI agent can open a PR. It cannot merge, buy adoption, or override review.

Support
