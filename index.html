Prompt Vote Lab tests whether a public prompt market can guide a constrained AI coding run. People propose prompts, vote with GitHub reactions, and eligible winners are implemented in a small static lab.

Current operating model

Small surface, strict checks

  • Implementation runs edit only lab/index.html, lab/style.css, and lab/app.js.
  • No external scripts, CDNs, trackers, cookies, or runtime API calls are allowed in the lab.
  • Merge is manual. Failed or rejected runs are still useful experiment data.

Weekly threshold

A prompt must beat the no-change baseline

Every weekly vote includes a virtual candidate: No change this week. It starts with 20 virtual votes. If that baseline wins, the workflow records a summary, creates no implementation PR, and spends no API budget.

Loop

How it works

One primary path: propose, vote, run, review, record. The page avoids extra choices so first-time visitors can understand the experiment quickly.

Propose

Create a GitHub Issue with the prompt and the expected visible result.

Vote

Use GitHub reactions. The top real prompt must beat the 20-vote baseline.

Run

The fixed implementation model edits only the static lab files.

Check

Safety and static-site checks run before the implementation PR is proposed.

Review

The maintainer reviews the PR and decides merge, reject, unsafe, failed, or no-change.

Record

The result and expectation gap are logged for later comparison.

Safety constraints

The AI is not given a blank check

The point is not to let an agent do anything. The point is to test whether useful changes emerge under stable, reviewable constraints.

  • Allowed: static HTML, CSS, vanilla JavaScript, local state, and JSON export/import inside the lab.
  • Blocked: external scripts, CDNs, network fetches, WebSockets, cookies, iframes, eval, and hidden trackers.
  • Scope: implementation PRs must stay inside lab/.
  • Budget: API runs are single-shot with retries disabled.
