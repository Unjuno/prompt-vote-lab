# Repository cleanup inventory

## Purpose

This inventory turns the repository 5S policy into a concrete cleanup map.

It is intentionally conservative. It classifies files and cleanup candidates before deletion.

No file should be deleted only because it looks old. Deletion requires a protected-evidence check, a canonical/legacy check, and a passing cleanup PR.

## Inventory states

| State | Meaning | Default action |
|---|---|---|
| Protected evidence | Public or audit evidence that must remain inspectable | Keep |
| Canonical active | Current implementation, policy, or operator surface | Keep and harden |
| Legacy fallback | Non-canonical path still needed as a fallback during migration | Keep with explicit legacy wording |
| Generated snapshot | Machine-written public output derived from repository or GitHub state | Keep unless regenerated by the owning workflow |
| Cleanup candidate | Candidate for consolidation, relabeling, or later removal | Track before changing |
| Not-yet-removable | Should eventually be removed, but only after a release gate | Keep until the gate is satisfied |

```text

```

## Generated snapshots

Generated snapshots are not source-of-truth policy. They should be changed by their owning generator or workflow.

| Surface | Path | Owning flow |
|---|---|---|
| Public result JSON | `data/public-results.json` | Public Results Export |
| Public result Markdown | `data/public-results.md` | Public Results Export |
| Comparison dashboards | `lab/comparisons/**` | Comparison dashboard builder |
| History pages | `lab/history/**` | Public results or dashboard builder |
| Support unlock records | `data/support-unlocks/*.json` | Support Unlock Export |
| Run records | `runs/*.md` | Weekly or manual run logging |

Cleanup PRs should not hand-edit generated snapshots unless the PR is explicitly a generated snapshot update.

## Cleanup candidates

These are candidates for future cleanup work. They are not deletion instructions.

| Candidate | Current risk | Required next step |
|---|---|---|
| Older canary workflow family | Many workflows make the canonical path harder to see | Add a workflow-family map before deletion |
| Duplicate status wording across docs | Drift between weekly automation, operator runbook, and README | Consolidate wording around one primary doc and contract tests |
| Legacy runner references | Readers may mistake fallback for canonical evidence | Keep explicit non-canonical wording in every reference |
| Temporary canary environment variables | Can survive after verification and confuse operators | Add cleanup notes where variables are introduced |
| Historical policy documents | Can be mistaken for active policy | Preserve but label as historical or compatibility evidence |

## Cleanup PR rule

A cleanup PR should include this five-line statement in its body:

```text
Sorted:
Set in order:
Shined:
Standardized:
Sustained by:
```

If a cleanup PR removes a file, it should also state:

```text
Protected evidence check:
Canonical/legacy check:
Generated snapshot check:
Removal gate:
Rollback path:
```
